# 新运动卡协议与源码核对

本次 Demo 只发送 `0x01 / 0x00` 的 100 字节通信查询。它不发送状态轮询、运动、回零、使能、输出、电机参数、重启或升级命令。正常 App 回复必须通过固定长度、校验、命令、令牌和完整 72 字节回显关联后，才显示通信成功。

核对日期：2026-10-26。结论来自归档中的 C 固件、C# Demo 和协议表的静态读取；没有运行厂商程序，没有连接运动卡，没有进行硬件动作。用户实际烧录版本仍需现场确认。

## 主机接口与网络默认值

主机通过普通以太网 **UDP** 与卡通信；卡再控制 EtherCAT 驱动器。Demo 不在 PC 上实现 EtherCAT 主站。

三轴 `Eth_Drive/Eth_Drive_001.c:466` 的 `Load_Net_Parameters` 定义：

|端点|资料默认值|
|---|---|
|运动卡|`192.168.8.20:5000`|
|PC 接收端|`192.168.8.12:6000`|
|掩码/网关|`255.255.255.0` / `192.168.8.1`|

同文件 `Socket_UDP` 将目标地址固定写入 W5500 的目标寄存器，卡不会自动把回复改发给请求来源的 IP/端口。汇川包中该文件与三轴 309 逐行一致。厂商 C# `Form1.cs` 的 `Udp_Initial` 也使用上述四个值。IP 可在新 Demo 中配置用于适配现场，但不代表卡内配置同步改变。

**真实 UDP 负载不包含 W5500 内部的 8 字节来源信息。** 协议表的发送方向偏移 `0..7` 标注“发送方信息”，是卡接收缓存中的元信息。App `Eth_File/Eth_Task.c:420` 读取后减去 8，再以 `+8` 访问有效负载；C# `UDP_AllUse_Send.cs` 直接发送负载。把表内那 8 字节再发到网络会导致帧错位。

## 本 Demo 实现的 0x01 查询

固定发送和接收 **100 字节**。下面所有偏移均从真实 UDP 负载第一个字节开始计数。

|偏移|请求|App 正常回复|
|---|---|---|
|0|字 `1..99` 累加后取低 8 位|同左|
|1|`B5`，上电查询标志|`A5`，App 标志|
|2..3|总长度 `00 64`，大端|`00 64`|
|4|主命令 `01`|`01`|
|5|副命令 `00`|`00`|
|6|本次令牌，`00..F0`|必须相同|
|7|`00`|ACK，必须为 `00`|
|8..11|挑战数据的一部分|窗口编号，u32 小端|
|12..15|挑战数据的一部分|App 源码设为零|
|16..79|挑战数据剩余部分|从请求 `8..71` 复制的挑战数据|
|80..87|请求补零|从请求 `72..79` 复制的挑战数据|
|88..99|请求补零|App 源码补零|

因此请求挑战范围是 `8..79`，完整回复回显范围是 `16..87`，均为 72 字节。表中分段仅为说明窗口字段位置；实现使用完整范围一次复制和比较。请求 `80..99` 固定为零。

关键源码：三轴/SCARA/四轴的 `Eth_File/Eth_Task.c:236`，函数 `Eth_Set_PowerUp_Bypass_Cmd`；对应 `case 0x01` 分别约在 `508`、`508`、`509` 行。三个 App 的这个函数和分支相同；汇川函数也相同，其分支因调试代码增补移到约 `517` 行。该分支只构造并发送回复，没有运动调用、参数写入、重启或使能调用。

App 接收端允许 `A5` 和 `B5` 两种请求标志。这里按协议表的上电查询选择 `B5`；回复标志才用于识别运行程序。

协议实现入口：

```csharp
byte[] CardProtocol.BuildEchoRequest(byte token, byte[] challenge);
EchoReply CardProtocol.ParseEchoReply(byte[] packet, byte token, byte[] challenge);
```

`EchoReply` 仅返回 `Marker` 和 `WindowId`。窗口是固件内部页面标识，不能解释为伺服就绪、回零完成或物理安全。

解析器拒绝不等于 100 字节的包、长度头不符、校验错、错误标志、命令/副命令/令牌不符、非零 ACK、任何一字节挑战不符。参数本身非法时抛 `ArgumentException` 系列异常；收到错误或不相关帧时抛 `ProtocolException`。当前实现不提供通用命令构造器、任意原始数据发送入口或 `0x10` 请求构造器。

累加校验是传输差错检测；令牌加本次随机挑战用于关联回复。它们不提供设备身份认证或加密。

## 为什么收到 Boot 也判为未通过

这项差异已直接核对 **Boot 017 源码**。`UserC/Eth_Task.c:636` 的 `case 0x01` 先把 84 字节备份区全部设为零；`Eth_Set_PowerUp_Cmd:125` 把这块零区复制到回复 `16..99`。Boot 使用 `B5` 标志、100 字节回复，回送令牌和窗口，却 **不回显挑战**。

所以 Boot 无法满足本 Demo 对完整挑战关联的成功条件。解析器会先验证其长度、校验、命令、令牌和 ACK，再明确报告“收到 Boot 格式回复；Boot 不回显挑战，未验证 App 通信。不要刷写或运动。”即便某个 `B5` 包伪造了相同挑战，也不作为 App 成功结果。此查询不会让卡退出 Boot，也不会继续发送升级包。

协议表将 Boot 回复中的大部分区域列为预留；本次以实际 Boot 017 分支为行为依据。不能为了让界面显示成功而放宽回显校验。

## 已识别但未发送的其他帧

以下内容用于之后排查和扩展，不表示本版本可以发送或已现场验证。

**常规状态 `A5 / 10 / 00`**：厂商 Demo 发 100 字节，App 正常回 300 字节。三轴 `Eth_Task.c:520` 会把请求 `7..19` 存入 `GtActiveRptDataLast`，作为主动上报是否需要重发的依据，具有通信缓存副作用。不能称为完全不改变内部状态。

|300 字节回复偏移|固件含义|
|---|---|
|7|ACK 0|
|8 / 9|EtherCAT 初始化/周期通信状态|
|10..15|6 个轴故障标志|
|16 / 17|初始化/回零错误编号|
|18..29 / 30..41|6 个控制字/状态字，u16 小端|
|42..71|6 组坐标，每组 sign 一字节 + 幅值 u32 小端|
|72..77|6 个原点传感器状态|
|78|固件的整体回零完成标志|
|79..299|普通版本预留；汇川修改版有扩展，禁止按同一布局推断|

坐标正负位 `0` 非负、`1` 负。三轴 `RunReadCurrent`（`ECAT_AxisControl.c:4888`）从轴脉冲转换，线性轴通常以微米计；不能根据槽名就认定为末端笛卡尔坐标。未配置轴槽也保留在报文中，不能从固定六槽推断实际有六轴。

普通 309 的原点读取底层为 TxPDO 的 `u8In` 第 2 位（`ECAT_Drive/ECAT_DriveAPI.c:1319`），轴控包装 `ECAT_AxisControl_GetOriginSensor:2155` 仍临时关闭/打开周期通信。汇川不同，见下文。不能推断高频查询对运行时序绝对无影响。

**主动状态 `C5 / 91`**：`Eth_Task.c:1299` 的 `ActiveRptDataProc` 在主循环比较状态变化，发送 18 字节：`5..6` 输入 u16 小端，`7..12` 六轴运行状态，`13` 回零中位图，`14` 拱门，`15` 联动，`16..17` 输出 u16 小端。它没有普通应答的副命令/令牌/ACK 布局；不能套用 `A5` 帧结构解析。

**不能发送的写操作**：`38` 重启、`39` 跳 Boot、`64` 拱门、`68` 单轴运动/回零、`70` 输出、`71` 联动、`72` 脉冲当量、`73` 行程，以及 Boot 文件/字符串命令。串口源码也有大量单字母运动调试命令，不能以“串口测试”名义任意发送。

## 各固件不能混用的差异

**四轴龙门**：在常规三轴版本上增加 A 轴相关行程、拱门目标和速度数据；整体回零完成条件也增加第 4 轴（`Eth_Task.c:617`）。`Gu32MaxTravel` 从 3 项扩成 4 项，脉冲当量/行程设置循环范围不同。四轴运动帧不能直接按三轴长度和布局发送。A 轴示例采用角度相关脉冲当量，不能直接套用线性轴的 mm。

**SCARA**：`Scara/Scara.c:33/89` 存在正逆运动学，联动过程调用逆解后把角度转换为脉冲（`ECAT_AxisControl.c:2597` 等）；`UserC/UserGlobal.c:61` 固定示例臂长 `194.307 / 139.750`，零角偏置 `-105.079 / 144.837`。这些只属于资料中的样机，不适用于用户旧四轴机械臂。状态读回仍来自轴脉冲；不能把前两个槽直接标为末端 X/Y。SCARA 第 2 轴的行程方向还有单独处理。

**汇川三轴**：外部 UDP 默认值与 `0x01` 回显仍相同，但 `0x10` 回复 `79..84` 新增来自对象 `6061` 的六轴模式显示，其后是切模/回零/缓存调试字节（`Eth_Task.c:630`）。原点读数变为缓存；应答后仅在 XYZ 全停止时轮流更新一个轴（`685..695`）。底层用 SDO 读取 `60FD` 数字输入第 2 位（`ECAT_DriveAPI_GetOriginSensor:1374`），运动时缓存可能过时。

汇川包的 `ECAT_DriveAPI.h:74` 起更换 IS620N 对象字典映射，包括电子齿轮 `6091`、极性 `607E`、转矩 `6072`、保存 `200C`，并在固件中反转位置/目标位置方向。初始化还写多项增益和丢同步容差（`ECAT_DriveAPI.c:581`，`WriteIS620NGainParam:650` 起）。它是实质修改版，不能因名称/主版本相同就用于其他驱动器。

## 现场前必须保留的判断边界

这次核查证明的是归档所示协议与 Demo 自身发送范围，不能证明板卡已烧入相同程序、四个电机与资料匹配、单位/方向正确、传感器有效或物理急停可靠。

固件本身上电约 2 秒就启动 EtherCAT 初始化（普通 `ECAT_AxisControl.c:1123`），会比对、写入细分/方向，必要时保存 EEPROM（约 `1245` 行起）；汇川初始化还写驱动增益。因此“本 Demo 只发通信查询”不能推导成“板卡已有程序绝不使能、写参数或动作”。软件显示的停止也不是物理急停或 STO 证据。

旧四轴机械臂的电机类型、驱动器型号、机械拓扑、编码器/减速比、零位、硬限位和电磁末端 IO 映射，均需另外核实。本次不从“SCARA”或“四轴龙门”文件名自动选择运动固件。
